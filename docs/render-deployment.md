# Deploying on Render (Docker)

This document describes deploying the full CRM-WhatsApp stack to
[Render](https://render.com) using the checked-in [`render.yaml`](../render.yaml)
Blueprint. It is an alternative to the Docker Compose deployment in
[`DEPLOYMENT.md`](../DEPLOYMENT.md).

Render builds each service from the repo's existing Dockerfiles and runs them as
independent services on its private network. TLS, load balancing and the public
`https://<service>.onrender.com` URLs are provided by Render, so the `nginx`
service from docker-compose is not needed.

## Service mapping

| docker-compose service | Render service  | Type                | Public? |
| ---------------------- | --------------- | ------------------- | ------- |
| `mysql`                | `crm-mysql`     | Private service + disk | no   |
| `redis`                | `crm-redis`     | Managed Key Value   | no      |
| `backend` (HTTP)       | `crm-backend`   | Web service         | yes     |
| `backend` (queue)      | `crm-worker`    | Background worker   | no      |
| `backend` (scheduler)  | `crm-scheduler` | Cron job (every min)| no      |
| `whatsapp-gateway`     | `crm-gateway`   | Web service + disk  | yes     |
| `frontend`             | `crm-frontend`  | Web service         | yes     |
| `nginx`                | —               | not needed          | —       |

All services are pinned to the **oregon** region so they share a private
network. If you change the region, change it for every service **and** the Key
Value instance.

## Prerequisites

- A Render account with a **paid workspace**. Private services, background
  workers, cron jobs and persistent disks are not available on the free tier,
  and free Key Value instances have no persistence.
- The repo connected to Render (GitHub/GitLab/Bitbucket).
- Two secrets ready to paste when prompted (see below).

## Deploy

1. In the Render Dashboard: **New → Blueprint**.
2. Select this repository and the branch to deploy.
3. Render reads `render.yaml` and shows the services it will create. It will
   prompt for the two values declared with `sync: false`:

   | Variable                    | How to generate                                   |
   | --------------------------- | ------------------------------------------------- |
   | `APP_KEY` (backend)         | `php artisan key:generate --show` (keep the `base64:` prefix) |
   | `CREDENTIALS_ENCRYPTION_KEY` (gateway) | `openssl rand -hex 32` (64 hex chars)  |

   Every other secret (`INTERNAL_GATEWAY_TOKEN`, `INTERNAL_SHARED_SECRET`,
   `MYSQL_PASSWORD`, `MYSQL_ROOT_PASSWORD`) is generated by Render and shared
   between services via `fromService`, so they cannot drift.

4. Click **Apply / Create**. Render provisions everything and builds the three
   images.

### First-deploy ordering

The `crm-mysql` private service can take a few minutes to initialize its disk on
the very first boot. The backend's pre-deploy hook (`render-entrypoint.sh
migrate`) retries the migration for up to a minute, so a slow database start
does not fail the deploy. If a first deploy does fail for that reason, just
trigger **Manual Deploy → Deploy latest commit** once MySQL is available.

## URLs

Render assigns `https://<service-name>.onrender.com`. The Blueprint assumes:

| Service      | URL                                    |
| ------------ | -------------------------------------- |
| frontend     | `https://crm-frontend.onrender.com`    |
| backend API  | `https://crm-backend.onrender.com`     |
| gateway      | `https://crm-gateway.onrender.com`     |

These strings are baked into `render.yaml` (see the header comment in that file)
because:

- the frontend's `NEXT_PUBLIC_*` values are inlined at **build** time, and
- the gateway/backend call each other by full URL.

**If a name is already taken in your workspace, Render appends a suffix** and
these URLs will be wrong. In that case, or after attaching custom domains
(below), update the corresponding values in `render.yaml` and redeploy:

- `crm-frontend` → `NEXT_PUBLIC_APP_URL`
- `crm-frontend` → `NEXT_PUBLIC_API_URL` (backend), `NEXT_PUBLIC_SOCKET_URL` (gateway)
- `crm-backend`  → `APP_URL`, `WHATSAPP_GATEWAY_URL` (in the `crm-backend-env` group)
- `crm-gateway`  → `LARAVEL_INTERNAL_API_URL`, `SOCKET_CORS_ORIGIN`
- `crm-backend-env` → `FRONTEND_URL`, `SANCTUM_STATEFUL_DOMAINS`

With custom domains, use e.g. `https://app.example.com`,
`https://api.example.com/api/v1` and `https://gateway.example.com`.

## Persistent data

| Data                        | Where it lives                              | Persists? |
| --------------------------- | ------------------------------------------- | --------- |
| MySQL data                  | `crm-mysql` disk at `/var/lib/mysql`        | yes       |
| WhatsApp session/auth creds | `crm-gateway` disk at `/app/sessions`       | yes       |
| Message media (`STORAGE_PROVIDER=local`) | gateway container filesystem    | **no**    |
| Workspace logos / report exports (`FILESYSTEM_DISK=local`) | backend container | **no**  |

The default `local` storage is convenient for a first deploy but **ephemeral**:
media uploaded between deploys is lost. For durable media, use the existing
Azure Blob integration:

- On **crm-gateway** set `STORAGE_PROVIDER=azure`.
- On **crm-backend** set `FILESYSTEM_DISK=azure` (in the `crm-backend-env`
  group).
- Fill in `AZURE_STORAGE_CONNECTION_STRING` (or `AZURE_STORAGE_ACCOUNT_NAME` +
  `AZURE_STORAGE_ACCOUNT_KEY` + `AZURE_STORAGE_URL`) and
  `AZURE_STORAGE_CONTAINER_NAME` on **both** services. They must point at the
  same container.

Both containers validate their storage config at boot (`php artisan
storage:verify` / the gateway's env schema), so a half-configured Azure setup
fails to start instead of silently dropping media.

> The gateway's disk is required: without it, every WhatsApp account must be
> re-paired after each deploy. Adding a disk also disables zero-downtime deploys
> for that service, so gateway redeploys have a few seconds of downtime.

## Using an external/managed MySQL instead

The bundled `crm-mysql` private service keeps the stack self-contained. To use
a managed MySQL (PlanetScale, Aiven, DigitalOcean, AWS RDS, …):

1. Delete the `crm-mysql` block from `render.yaml`.
2. On **crm-backend**, replace the four `DB_*` `fromService` entries with the
   external host/credentials. Put them in the `crm-backend-env` group if you
   prefer, e.g.:

   ```yaml
   - key: DB_HOST
     sync: false
   - key: DB_DATABASE
     value: crm_whatsapp
   - key: DB_USERNAME
     sync: false
   - key: DB_PASSWORD
     sync: false
   ```

   (`sync: false` prompts you for the value in the dashboard.)
3. On **crm-gateway**, replace the `MYSQL_*` `fromService` entries with the same
   host/credentials (the gateway reads `MYSQL_*`, the backend reads `DB_*`).
4. Most managed MySQL providers require TLS; set `MYSQL_ATTR_SSL_CA` (backend)
   and enable TLS on the gateway's MySQL connection as needed.

## Verify after deploy

```bash
curl -f https://crm-backend.onrender.com/api/v1/health
curl -f https://crm-gateway.onrender.com/healthz
curl -f https://crm-frontend.onrender.com/
```

Then in the app: log in, pair a WhatsApp account (scan the QR), send/receive a
message, confirm Socket.IO reconnects, upload media, and confirm queued jobs run
(campaigns / exports).

## Updating

Push to the connected branch (or **Manual Deploy** in the dashboard). Each
service has a `buildFilter` so only the services whose files changed rebuild.
Migrations run automatically via the backend pre-deploy hook.

Changing any `NEXT_PUBLIC_*` value requires a **rebuild** of `crm-frontend` (the
values are compiled into the bundle), not just a restart.

## Notes and limitations

- **Region.** All services + Key Value must share a region for private
  networking.
- **Compute plans.** The Blueprint uses `1c-2g` for the app services and
  `256mb` for Redis. Adjust `plan:` per service as needed; they can be changed
  in the dashboard later.
- **Migrations.** Applied only by `crm-backend`'s pre-deploy hook (not the
  worker or cron), to avoid concurrent schema changes.
- **Laravel web server.** The backend image runs `php artisan serve`
  (`PHP_CLI_SERVER_WORKERS=4`). This is fine for low/medium traffic; for higher
  throughput, replace it with PHP-FPM + a lightweight web server in the image.
- **Backups.** Back up MySQL with `mysqldump` (see
  `infrastructure/scripts/mysql-backup.sh`). Do **not** rely on disk snapshots
  for a database — Render's docs explicitly warn against restoring a snapshot of
  a disk that backs a database.
